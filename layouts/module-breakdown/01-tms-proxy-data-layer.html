Module purpose

TMS Proxy / Data Layer

Provide a stable local service boundary between the browser modules and FortuneLogy TMS, normalize access patterns, and host supporting operational datasets.

Upstream data→TMS Proxy / Data Layer→Downstream handoff

Inputs / Data

  • TMS credentials: UserID and UserToken
  • TMS read/write endpoint requests
  • Orders, trips, manifests, stops, drivers and terminal reference data
  • Local brokerage, equipment and analytics files

Core workflow

Browser posts login and operational requests to the local proxy
Proxy relays TMS reads and most writes; specialized handlers save manifests and check in tasks
Responses are translated into browser-side order, trip and resource state
Operational events feed the main dashboard, Dispatch, Audit and Analytics views

Key business logic

  • Token is the effective credential and is sent per request
  • The documented global cookie jar is vestigial; token-only calls return full data
  • TMS can return an empty JSON array with HTTP 200 when a token is stale
  • Manifest updates rebuild a complete multi-field payload and preserve untouched rows

Outputs / Next step

  • Normalized data to Orders, Linehaul Manager, Dispatch and Analytics
  • Write results for trip creation, manifest editing and check-in

KPIs

  • API latency
  • Data freshness
  • Authentication failures
  • Empty-response anomaly rate
  • Endpoint error rate

Alerts / Exceptions

  • Treat unexpected empty responses as possible token expiry
  • Avoid negative-caching failed trip detail or load totals
  • High-volume order detail calls create an N+1 performance risk
